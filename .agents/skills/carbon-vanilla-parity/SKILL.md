# Carbon Vanilla Parity

Use this skill for parity work in the Carbon native port of the supplied Minecraft Java Edition 26.3 source. Verify the actual source tree and version metadata before choosing behavior. The target is this exact Java Edition source, not another release or Bedrock. A component result only covers the exercised behavior; never describe the whole game as parity-complete.

Start with `PORT_STATUS.md`, the relevant implementation and tests, and `tests/run_all.py`. Keep evidence tiers distinct: unmodified supplied Java classes compiled with only unrelated-dependency stubs; methods extracted from supplied Java sources; source-adapted JVM oracles; handwritten source-derived models; Carbon-native assertions; visual smoke tests; and performance measurements. State exactly which tier supports each claim. A JVM model is not Minecraft execution, an assertion is not differential testing, a visual smoke test is not gameplay parity, and a hidden-window CPU timing is not visible FPS. Do not strengthen an existing test's claim merely because it is in `*_parity.py`.

The helper scripts and references are bundled beside this loaded `SKILL.md`; do not assume they are present at the Carbon repository root. Resolve `<skill-root>` to the directory containing this file, and call its scripts by absolute path even when the current directory is Carbon or an isolated fixture. For test and oracle provenance, run `python "<skill-root>/scripts/parity_tools.py" inventory --workspace "<Carbon-root>"`. Its checked-in manifest is declarative evidence labeling, not an automatic proof system. It compares declared test/source-file hashes with the hashes pinned at evidence review and marks labels stale or unreviewed after file changes; re-inspect the harness and source before updating a label. Verify the reported original source paths, supplied `version.json`, Java runtime, and source provenance for the code under test; hash the exact source files, jar, and relevant jar class entries when available. Decompiled source can differ from the supplied binary, so when a mismatch depends on exact implementation details, compare against an isolated execution of the relevant actual 26.3 jar classes where feasible and report which artifact is authoritative for the result. Discover JDK tools from PATH or explicit user/workspace configuration. Keep generated classes, harnesses, fixtures, and captures in an isolated build/temp directory. Read original source and assets in place; do not rewrite them.

For a direct jar oracle, run `python "<skill-root>/scripts/parity_tools.py" run-jar ...` to compile a deterministic Java driver against the supplied jar in a temporary directory; see the bundled [references/parity-tools.md](references/parity-tools.md).

When comparing structured outputs, run `python "<skill-root>/scripts/parity_tools.py" compare EXPECTED.jsonl ACTUAL.jsonl --schema SCHEMA.json` with an explicit schema. Require at least one deterministic case and a nonzero process exit for oracle build errors, missing outputs, or any mismatch; don't rely on console text that a caller may ignore. Require an explicit seed and action trace where applicable; serialize the full relevant state and ordering; compare Java float/double bits when the contract requires exactness, and allow a numeric tolerance only when justified and declared. Preserve UTF-16 behavior, signed overflow, evaluation order, identity/ordering rules, and round trips. Capture the first mismatch with a stable case ID and field path, then minimize it. Confirm a mismatch against an independent vanilla oracle before changing Carbon; never edit the oracle to make a failing port pass. Save the minimized fixture, source provenance, expected/actual values, and regression test. Re-run the affected harness and the appropriate broader checks after a fix.

Prefer executing unmodified vanilla classes or methods extracted directly from the supplied sources, with minimal stubs only for unrelated dependencies. A Java wrapper around handwritten C++-translated logic is not an independent oracle. If dependency-complete class execution is infeasible, label and explain the lower evidence tier, and pursue a real oracle before claiming parity. Coverage that lacks required Java behavior remains an explicit gap. Implement a gap only when requested or within the user's stated scope; prefer dependency-complete, source-faithful fixes and log unsupported or blocked work honestly rather than approximating Minecraft behavior. For an in-scope fix request, follow the isolated branch workflow in [references/workflow.md](references/workflow.md). Finding a bug during a read-only audit, review, or reproduction request does not authorize edits. An explicit request to run the verified-fix PR workflow authorizes its scoped feature-branch commit, push, and PR creation; honor earlier standing authorization in the session without asking again. A fix request without a PR request authorizes local scoped work only, and publication needs authorization before it occurs.

For renderer comparisons, record the source asset/version, exact viewport, GUI scale, camera, graphics backend, color format, capture stage, ROI, and meaningful pixel/color tolerance. For physics, compare fixed-tick (20 TPS) input traces, collision state, and per-tick results. World generation requires real seeds, settings, chunks, and the relevant density, aquifer, and surface pipeline; matching a noise sample alone is not terrain parity. Separate CPU time, GPU completion, and visible FPS, and state the measurement method.

Read [references/workflow.md](references/workflow.md) for the Carbon-specific source map, evidence inventory, and detailed comparison guidance. The comparator schema and commands are documented in [references/parity-tools.md](references/parity-tools.md).
